# CryptoChunk — authenticated erasure-coded file storage

**Course project:** Advanced Cryptography  
**Author:** Krishna Mahajan · Roll 106123070 · CSE, NIT Trichy

CryptoChunk is a runnable educational prototype for storing a file as fixed-size logical chunks, encoding each chunk into **4 data + 2 parity shards**, placing shards into six local node directories, and verifying shard integrity with SHA-256. It authenticates metadata with HMAC-SHA-256 and reconstructs a file when up to two shards per logical chunk are missing or fail checksum verification.

> **Scope:** the six “nodes” are separate directories on one machine. This demonstrates the storage and cryptographic logic, not a production networked distributed system. It does not provide confidentiality/encryption, authenticated remote node communication, Byzantine consensus, or key management suitable for production.

## Requirements

- Python 3.10 or newer
- No runtime third-party dependencies
- `pytest` is optional for tests

## Quick start

From the repository root:

```bash
python -m venv .venv
# Windows PowerShell: .venv\\Scripts\\Activate.ps1
# macOS/Linux: source .venv/bin/activate
python -m pip install -e .
```

Store a file:

```bash
cryptochunk store path/to/input.bin --storage ./storage --chunk-size 262144
```

Or without installing the console command:

```bash
PYTHONPATH=src python -m cryptochunk.cli store path/to/input.bin --storage ./storage
```

Simulate a corrupt shard and a missing shard (shard indexes are 0–5):

```bash
cryptochunk fault --storage ./storage --chunk 0 --shard 1 --action corrupt
cryptochunk fault --storage ./storage --chunk 0 --shard 4 --action remove
```

Restore and verify:

```bash
cryptochunk restore --storage ./storage --output ./restored.bin
```

The restore command verifies the HMAC on the manifest, checks every shard against its SHA-256 digest, reconstructs from any four valid shards, verifies each reconstructed logical chunk and the complete output, and repairs missing/corrupt shard files when reconstruction succeeds.

## Implemented functionality

- Fixed-size logical chunking, including empty files and final partial chunks.
- Systematic 4+2 Reed–Solomon-style erasure coding over GF(2^8), implemented in this repository.
- SHA-256 checksums for every stored shard, each original chunk, and the original complete file.
- HMAC-SHA-256 authentication of canonicalized manifest JSON.
- Six separate local storage-node directories and deterministic shard-to-node placement.
- Detection of absent, truncated, or altered shards.
- Recovery from any two unavailable/corrupt shards per logical chunk, followed by shard repair.
- CLI fault injection for demonstration and repeatable tests.
- Test coverage for all 15 choices of four shards, recovery, manifest tampering, and unrecoverable loss.

## Cryptographic and engineering notes

- **SHA-256** detects accidental or malicious changes to shard bytes when compared with trusted metadata. Hashes alone do not authenticate the metadata.
- **HMAC-SHA-256** authenticates the manifest using a 256-bit key in `manifest.key`. Keep that key outside any untrusted storage boundary in a real deployment. In this demo the key sits beside the manifest for convenience, so the demo does not protect against an attacker who can replace both files.
- **Erasure coding is not encryption.** Anyone who can read enough shards can reconstruct the plaintext. Add authenticated encryption (for example, an established AEAD construction) before storage if confidentiality is required.
- This implementation uses a systematic generator matrix with four identity rows and two parity rows over GF(256). A stripe is recoverable if at least four valid shard indexes remain.
- The prototype loads the input file into memory. For very large files, streaming I/O, atomic writes, quota controls, concurrency, and crash-safe manifest updates should be added.

## Evaluation

Run `python scripts/benchmark.py` to generate a CSV with timing, storage overhead, and recovery outcomes for sample sizes. Results are machine-dependent and should be reported with the environment in the final submission. The baseline raw storage overhead for 4+2 coding is approximately **50%** for large files (six shards for four data shards), excluding small metadata and padding effects.
